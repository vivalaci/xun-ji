## Context

内置动作库 `config/exercises.js` 是打包进小程序的静态常量（100 动作，`EXERCISES` 数组），`utils/exerciseLib.js` 把它与每用户私有的 `custom_exercises` 云集合合并查询。运行中的小程序改不了自己的代码，所以"App 内编辑动作库"必须引入云端数据。

现状约束：项目**无任何云函数**（`project.config.json` 声明了 `cloudfunctionRoot` 但目录不存在），4 个集合全是每用户私有，`utils/db.js` 全程客户端直连 `wx.cloud.database()`。本变更引入首个云函数与首个跨用户共享集合，故设计需谨慎。

驱动力明确：**不想为纯内容调整等微信审核**。服务端驱动内容是该场景的标准解法。

## Goals / Non-Goals

**Goals:**
- 所有者（单一 openid）在 App 内改名/改分类/改别名/隐藏内置动作、新增全局动作、编排类别顺序，改动不发版即对所有用户生效。
- 真安全边界：非所有者**无法**篡改全局动作库。
- 常态云开支≈0（正常用户不触发云函数）。
- 历史记录完整性绝对不破。

**Non-Goals:**
- 不把 100 个动作搬去云端（见 D1）。
- 不做多管理员、角色系统、审计日志（单人场景，过度设计）。
- 不允许删除内置动作、不允许改动作 id（只允许隐藏）。
- 不管理每用户私有的 `custom_exercises`（那是用户自己的数据）。

## Decisions

### D1：覆盖层（只存差异），不把动作库全量搬到云端
`config/exercises.js` 继续做基线随包发布；云集合 `exercise_overrides` 只存差异（patch / 全局新增 / 类别排序）。合并顺序：**（内置 + 拼全局新增）→ 套 patch → 拼每用户自建**——patch 在全局动作拼入后套用，因此对内置与全局动作（`gbl_`）均生效：管理员新增的全局动作也能用同一 patch 机制改名/改类/隐藏，无需第二套「编辑全局动作」的写入动作（实现时定，与提案初稿「内置→patch→全局」为超集关系，仅扩展了 patch 的作用面）。
- 备选：把 100 动作全量迁到云集合，客户端纯云端读。否决：伤离线与冷启（无网新用户看不到任何动作）、动到每条读路径、100 条静态数据放云端徒增读次数与失败面，收益为零。
- 收益：离线兜底天然成立（最坏情况看到未改名的基线）；改动面收敛在合并层。

### D2：安全边界在云函数，不在客户端
`exercise_overrides` 集合权限设「**所有用户可读，仅管理端可写**」——客户端连写的能力都没有。写入只经云函数 `exerciseAdmin`，函数内校验 `cloud.getWXContext().OPENID === ADMIN_OPENID`。OPENID 由微信基础设施注入云函数上下文，**客户端无法伪造**，这是真边界。
- 备选：客户端判断 openid 后直接写集合。否决：小程序代码在用户设备上可被篡改，等于任何人都能改全体用户的动作库——**不是安全设计**。
- `ADMIN_OPENID` 存云函数**环境变量**（不进代码、不进 git）。环境变量本身零开支。
- 先有鸡蛋问题：首次需先知道自己的 openid → 部署后调一次云函数令其回显，或云开发控制台查（见 tasks）。

### D3：管理入口用隐藏手势触发，避免按用户数产生云函数调用
客户端无法直接取 openid（无云函数就拿不到），若每次启动调云函数问"我是不是管理员"，**调用次数随用户数线性增长**——为单人功能让全体用户掏调用费，不可接受。改为：动作库页**隐藏手势**（如标题连点 5 次）才触发云函数验证并进管理模式。正常用户永不触发 → 调用次数≈0。
- 客户端这道门**不担安全职责**（真门在 D2），做成隐藏零安全损失。
- 常态新增开支仅 `exercise_overrides` 每用户每次启动一次读（走既有 `getCache` + `refresh`），量级可忽略。

### D4：架构铁律 1 开例外——管理写入走云函数直调，不走本地先写队列
铁律 1 规定云读写只走 `utils/db.js`（写用 `saveLocalFirst` 乐观队列）。管理写入是**服务端权威的共享内容**，本地先写一个所有人可见的数据没有意义，且集合权限本就禁止客户端写。故：
- **读**：`exercise_overrides` 仍走 `db.js`（缓存优先 + refresh），遵守铁律。
- **写**：客户端 `wx.cloud.callFunction` 直调，配真实 loading/失败态（不乐观、不排队）。
- 该例外须同步写进 `CLAUDE.md` 与 `docs/06/07`，避免后人误读为破例先例。
- 备选：把云函数调用也包进 db.js。可考虑（收敛调用点），但语义与 db.js 的"集合 CRUD + 本地优先"模型不同，倾向单独 `utils/adminApi.js` 薄封装，实现时定。

### D5：hidden 语义——从列举/搜索消失，但按 id 必须仍能解析
`byCategory`/`searchExercises`/动作选择面板 排除 hidden；`getExercise`/`getName` **仍返回该动作**。否则隐藏一个动作，所有引用它的历史记录立刻退化成「已删除动作」占位，破坏历史完整性（铁律 3 的兜底本是给"用户删自建动作"用的，不该被管理操作触发）。

### D6：三大项禁止隐藏
`MAIN_LIFTS`（bench/squat/deadlift）与首页三大项曲线硬绑定，隐藏将使所有用户首页塌陷。云函数**服务端**拒绝对 `MAIN_LIFTS` 的 `hidden:true`（不能只靠客户端 UI 灰置）。改名/改分类不受限（id 稳定、category 仅展示）。

### D7：`有氧` 置末规则保留；全局动作 id 用 `gbl_` 命名空间
`byCategory` 现有的「`有氧` 恒置末」硬规则保留，`kind:'categories'` 的 order 只排非有氧类别。全局新增动作 id 前缀 `gbl_`，与每用户自建的 `cus_` 明确分开，杜绝命名空间碰撞。

### D8：自建动作编辑为管理员专属，能力对齐内置动作；写走本地先写；不做 cus_ → gbl_「升格」
实现期扩展（所有者验证时提出）：自建动作除删除外应可编辑，且**仅对管理员开放**——普通用户对自建动作维持仅删除（产品决定：编辑是内容管理能力，统一收在管理模式下，入口一致、心智一致）。编辑内容与内置动作对齐：改名/改分类/改别名/**隐藏**（hidden 同语义：列举/搜索排除、按 id 仍解析、可撤销）。
- 写通道：`custom_exercises` 是每用户私有集合，编辑走 `db.updateLocalFirst`（铁律 1 正道，不涉云函数）；效果仅作用于管理员自己的数据（管理员本就看不到他人自建动作）。动作 `id` 不可改，历史聚合不受影响。`aliases`/`hidden` 为可缺省新字段（老数据无感，合并层透传）。
- 备选一：对所有用户开放自建编辑。否决：所有者明确要求普通用户仅删除；且避免普通用户误触编辑面板的复杂度。
- 备选二：把自建动作「升格」为全局动作（cus_ → gbl_）。否决：改 id 会把该用户既有历史打成「已删除动作」；保留原 id 又违反 `gbl_` 命名空间且与私有文档双源冲突。确需全局版本时，由管理员直接新建 `gbl_` 动作即可。

## Risks / Trade-offs

- [基线与线上覆盖漂移] 长期看 `config/exercises.js` 与用户实际所见会分叉；将来发版改了 config，patch 仍叠加其上可能产生意外结果 → 约定：发版前审视现存 patch，必要时把已稳定的改动收敛回 config 并清掉对应 patch。v1 不做自动收敛工具。
- [首个云函数的运维面] 新增部署步骤（开发者工具上传）、`wx-server-sdk` 依赖、环境变量配置；本地 `node --check` 覆盖不到云函数逻辑 → 云函数保持极薄（校验 + 写入），业务判断（如禁隐藏三大项的名单）可复用纯函数并补单测。
- [冷启窗口内看到旧内容] 无网/首启时先渲染基线（未套 patch），overrides 到达后刷新 → 与项目既有"缓存优先 + refresh"体验一致，可接受。
- [管理误操作无回滚] 单人场景无审计/撤销，改错了得手动改回 → v1 接受；隐藏而非删除本身已是保守设计，误操作可逆。
- [合并层成为热路径] 每次取动作都要套 patch → patch 数量级小（几十条），合并结果可在 `exerciseLib` 内做一次性 memo，实现时留意。
